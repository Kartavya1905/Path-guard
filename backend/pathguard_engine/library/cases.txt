# PathGuard risk library: 100 realistic project use cases (10 domains x 10).
# Written from common project-management practice. These are illustrative examples, not recorded
# outcomes: there are no statistics or probabilities in them.
#
# Format:
#   ## domain
#   @ title | starting point | goal
#   T task (owner role) ; task (owner role) ; ...
#   R task# | category | risk title | trigger | consequence | control      (a risk a team accepted)
#   X task# | category | idea title | trigger | why it was rejected | -    (an idea a team rejected)
# Categories: scope, dependency, vendor, approval, testing, data, staffing, security, performance,
# compliance, communication, budget, schedule, quality, adoption, logistics, integration, release.

## software
@ Customer portal redesign | Redesign approved by product leadership | New portal live for all customers
T Finalize UX designs (Designer) ; Build front end (Frontend dev) ; Accessibility review (QA) ; Phased rollout (Product manager)
R 1 | scope | Late design changes | Stakeholders request new screens after sign-off | Front-end work is redone and the launch slips | Freeze scope after sign-off and route new requests to a backlog
R 3 | compliance | Accessibility gaps found late | Accessibility checks only run at the end | Fixes delay launch or exclude disabled users | Run automated accessibility checks on every pull request
R 4 | release | Rollout breaks existing bookmarks | Old URLs are not redirected | Customers hit error pages and contact support | Map old URLs to new ones and test redirects before rollout
X 2 | scope | Rewrite the backend at the same time | A developer wants to modernize everything | Doubles the work and the risk for no customer benefit | -

@ API version upgrade | Deprecation notice received for API v1 | All clients on the new API version
T Inventory API consumers (Tech lead) ; Implement v2 endpoints (Backend dev) ; Migrate client apps (Mobile dev) ; Retire v1 (Ops engineer)
R 1 | dependency | Unknown API consumers | Partners call the API without registering | Retiring v1 breaks partner integrations | Log callers for a month and contact every unknown client
R 3 | schedule | Mobile clients update slowly | Users do not install the new app version | Old app versions keep calling v1 after retirement | Keep v1 until app adoption is high enough and show an update prompt
R 2 | testing | Behaviour differences between versions | v2 changes defaults silently | Clients get different results and lose trust | Write contract tests that compare v1 and v2 responses
X 4 | release | Switch off v1 on a fixed date regardless | Management wants a clean cut-over | Ignores real client usage and would break partners | -

@ Internal tool replacement | Team agrees the old admin tool must go | Staff using the new admin tool daily
T Gather workflows (Business analyst) ; Build the new tool (Developer) ; Train staff (Team lead) ; Decommission old tool (Ops engineer)
R 1 | scope | Undocumented workflows | Staff rely on hidden features of the old tool | The new tool cannot do part of their job | Shadow each team for a day before writing requirements
R 3 | adoption | Staff keep using the old tool | Old habits and missing shortcuts | Data ends up split across two tools | Set a read-only date for the old tool and collect feedback weekly
R 4 | data | Data not migrated completely | Edge-case records fail to import | History is lost when the old tool is switched off | Reconcile record counts before decommissioning
X 2 | budget | Buy a large enterprise suite instead | A vendor demo looked impressive | Far beyond the team's needs and budget | -

@ Search feature launch | Search added to the product roadmap | Customers can find items with site search
T Choose search engine (Tech lead) ; Index existing content (Backend dev) ; Tune relevance (Data analyst) ; Launch to users (Product manager)
R 2 | performance | Indexing overloads the database | Full re-index runs during business hours | Site slows down for everyone | Index in batches overnight with rate limits
R 3 | quality | Poor relevance at launch | Ranking tuned on too little real data | Customers cannot find items and stop using search | Test with real queries from logs before launch
R 1 | vendor | Hosted search costs grow quickly | Pricing depends on query volume | Running cost exceeds the plan | Estimate volume early and set usage alerts
X 4 | scope | Add voice search in version one | A stakeholder saw it in a competitor | Adds complexity before basic search works | -

@ Monolith to services split | Architecture review recommends splitting the monolith | Orders module running as its own service
T Map module boundaries (Architect) ; Extract orders service (Backend dev) ; Set up monitoring (SRE) ; Cut traffic over (Tech lead)
R 1 | dependency | Hidden coupling between modules | Shared database tables used by many modules | The new service cannot change data safely | Map table usage before extraction and add an access layer
R 3 | performance | Network calls add latency | Calls that were in-process now cross the network | Checkout pages become slower | Measure latency budgets and add caching where needed
R 4 | release | Cut-over cannot be reversed easily | Data written by the new service diverges | Rolling back loses orders | Run both paths in shadow mode and keep a tested rollback
X 2 | scope | Split all modules at once | Team wants to finish the migration quickly | Too many moving parts to test safely | -

@ Feature flag platform adoption | Releases keep causing incidents | Every risky change ships behind a flag
T Select flag tool (Tech lead) ; Integrate SDK (Developer) ; Define flag policy (Engineering manager) ; Clean up old flags (Developer)
R 2 | performance | Flag checks slow requests | SDK fetches flags on every request | Pages get slower under load | Use local caching and streaming updates
R 3 | quality | Flags never removed | No owner or expiry on flags | Code becomes hard to reason about | Give every flag an owner and a removal date
R 2 | security | Flags exposed to the client | Sensitive flags evaluated in the browser | Users discover unreleased features | Evaluate sensitive flags on the server only
X 4 | schedule | Remove all old flags in one big change | Wanting a quick cleanup | Risky change touching many features at once | -

@ Payments reconciliation job | Finance reports mismatches each month end | Daily automated reconciliation in place
T Agree matching rules (Finance analyst) ; Build reconciliation job (Data engineer) ; Validate with finance (Finance lead) ; Schedule and monitor (Ops engineer)
R 1 | data | Matching rules unclear | Finance and engineering define a match differently | The job flags false mismatches | Write matching rules as examples signed off by finance
R 2 | integration | Bank file formats change | The bank updates its export format | The job fails silently | Validate file format on arrival and alert on failure
R 4 | communication | Nobody watches the alerts | Alerts go to a shared mailbox | Mismatches pile up unnoticed | Route alerts to a named owner with an escalation path
X 3 | scope | Rebuild the accounting system | A developer suggests replacing the ledger | Far larger than the actual problem | -

@ Open source library upgrade | Security scan flags an outdated framework | Application running on the supported framework version
T Review breaking changes (Tech lead) ; Upgrade and fix code (Developer) ; Run regression tests (QA) ; Deploy to production (Ops engineer)
R 1 | dependency | Plugins not compatible | Third-party plugins lag behind the framework | Upgrade blocked until plugins are replaced | Check every plugin's compatibility before starting
R 3 | testing | Regression tests too thin | Low automated coverage on old features | Bugs reach production after the upgrade | Add smoke tests for key journeys before upgrading
R 4 | release | Upgrade cannot be rolled back | Database changes made during the upgrade | A bad deploy forces an emergency fix | Separate schema changes from the code upgrade
X 2 | schedule | Upgrade every dependency at once | Fix all warnings in one go | Too many changes to debug if something breaks | -

@ Developer onboarding docs | New engineers take weeks to ship their first change | New engineers ship a change in their first week
T Audit current setup steps (Senior dev) ; Write setup guide (Developer) ; Automate local setup (DevOps engineer) ; Test with a new hire (Engineering manager)
R 2 | quality | Guide goes out of date | Nobody owns the documentation | New hires follow wrong steps | Review the guide every time the setup changes
R 3 | dependency | Setup depends on one laptop type | Script assumes one operating system | Some hires still cannot set up | Test the script on every supported operating system
R 4 | communication | Feedback never collected | New hires do not want to complain | Problems repeat for every hire | Ask each new hire for a short written review
X 1 | budget | Hire a full-time documentation writer | Docs feel like a big problem | The team is too small to justify it | -

@ Performance improvement sprint | Customers complain that pages are slow | Key pages load quickly for most users
T Measure current speed (SRE) ; Fix slowest queries (Backend dev) ; Optimize front-end assets (Frontend dev) ; Monitor after release (SRE)
R 1 | data | Measurements not representative | Testing only from the office network | Fixes target the wrong pages | Use real user monitoring data to pick targets
R 2 | quality | Fixes introduce bugs | Query rewrites change results | Customers see wrong data | Compare query results before and after each change
R 4 | performance | Speed regresses again later | No performance budget in the pipeline | Gains disappear within months | Add performance checks to continuous integration
X 3 | scope | Rewrite the front end in a new framework | Belief that the framework is the problem | Huge effort with uncertain benefit | -
